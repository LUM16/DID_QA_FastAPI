# 回答 👍/👎 反馈功能改动前后对比

## 改动概览

本次改动围绕回答卡片上的 👍/👎 反馈流程，重点是让负向反馈更容易填写、让反馈原因更明确，并把信号用于相似问题的后续 Cypher 生成。已有的案例存储和正、负案例检索机制得到保留。

## 改动前后

| 对比项 | 改动前 | 改动后 |
|---|---|---|
| 👎 反馈交互 | 通过浏览器对话框收集原因和可选说明，填写过程与回答卡片分离。 | 在回答卡片内展开反馈面板，直接选择原因并填写可选说明。 |
| 👎 原因和说明 | 原因通过对话框输入，选项和输入约束不够明确。 | 提供“查询逻辑、数据错误、数据缺失、人物错误、展示格式、其他”六类原因；必须先选原因才能提交。可补充最多 1,000 个字符的说明。 |
| 👍 反馈原因 | 正向反馈可能记录为通用的 `other`。 | 正向反馈统一规范为 `helpful`；若请求将 👍 与负向原因组合，API 会拒绝。 |
| 投票状态 | 用户较难确认当前投票状态，修改投票的状态提示不够清晰。 | 当前投票按钮会高亮，并通过 `aria-pressed` 暴露状态；用户可改投另一票，更新原案例。 |
| 请求状态 | 反馈保存时的控件状态及失败后的恢复不够完善。 | 保存期间禁用反馈控件；请求失败时显示错误提示，并恢复控件。 |
| API 输入校验 | 投票值主要按正负号处理，接受范围不够严格。 | 只接受 `1`（👍）或 `-1`（👎）；限制反馈说明长度，并校验反馈原因。 |
| 统计信息 | 可查看案例总数及 👍/👎 数量。 | 额外按投票方向统计反馈原因，便于了解常见负向反馈类别。 |
| 后续查询使用 | 已有正向案例和负向案例检索能力。 | 保留原有检索；负向案例可附带原因和说明，向生成模型提供更具体的避错上下文。 |

## 改动后的处理流程

1. 每次回答会关联一个案例记录，其中包含用户问题和生成的 Cypher。
2. 用户提交反馈后，系统把投票、原因和可选说明写入该案例；改投时更新同一案例的当前反馈。
3. 后续生成 Cypher 时，系统按问题相似度检索最多 3 条 👍 案例和 2 条 👎 案例，并将其作为提示词上下文。
4. `/api/stats` 返回按正向、负向分别汇总的反馈原因统计。

## 功能边界

- 反馈用于相似问题的提示词示例检索，不会对模型进行微调。
- 👎 不会自动重跑当前问题、应用用户提出的修正或修改 Neo4j 数据。
- 案例检索采用基于文本的 BM25 风格排序。投票可以提供参考信号，但不保证相似案例一定相关，也不保证后续答案必然正确。
- 本地反馈存储在 `data/memory/examples.sqlite3`；部署时若没有持久化该文件，重建环境后历史反馈可能无法保留。
- 确定性本地 Cypher 模板不会因反馈而自动改写。
